- Key-press haptics triage (Jan 2026): users reported “system haptics on, other apps vibrate, NSK doesn’t” (and specifically: arrows/mic vibrate but letter keys don’t). Likely failure mode: `performHapticFeedback(KEYBOARD_TAP/VIRTUAL_KEY)` can report “handled” while producing no physical haptics on some devices, causing NSK to skip vibrator-based haptics. Updated `ImePressEffects` to prefer `KEYBOARD_TAP` → fallback `VIRTUAL_KEY` (on both input view and container), and to _not trust_ view haptics return values in “use system vibration” mode (best-effort still calls view haptics, but always proceeds to the vibrator path for non-long-press taps). Also keep trying the vibrator even after a prior exception (resetting the error flag on `onStartInputView`). In “use system vibration” mode, if view haptics fail, fallback uses the user duration via `PressVibrator.vibrateFallback` (avoid relying on suppressed predefined clicks). Added/updated a Genymotion-friendly instrumentation check in `KeyPressHapticsInstrumentedTest`; still needs real-device verification + release. Details + hypotheses: `haptics_mystery.md`. Follow-up: some layouts emit key-presses with **no explicit keycode** (`primaryCode==0`) and rely on output-text; press effects used to skip code `0`, matching the “letters don’t vibrate/click” reports. - Neural next-word suggestions triage: mitigations implemented for the “empty until typing next letter” UX (manual-pick+space no longer clears the strip; selection updates from a pick no longer trigger the restart-word flow). Domain-token artifacts are filtered at the pipeline level (`CandidateNormalizer.normalizeForNextWordUx`), so engine + legacy sources don’t surface `com/http/https/www` in normal prose (unless the context is clearly URL-like). Next-word candidate pooling is now larger than the visible strip (aggressiveness mapping: minimal=8, medium=24, maximum=48) so reranking can pick a better top row. While composing, `SuggestImpl` injects prefix-matching candidates from the full pooled next-word list (not only the displayed next-word row) to make context-aware completions more reliable. Next-word suggestions now also run for “invalid” committed tokens when engines are inactive, so legacy personalization/contacts still work for names and other out-of-dictionary words. See `docs/triage/neural-next-word-suggestions-2026-01-19.md`. Helper: `scripts/adb_nextword_diagnostics.sh`.
- SwiftKey-like behavior notes (Jan 2026): NSK already has the core building blocks: persistent bigrams (`NextWordDictionary`), Presage (n-gram), and an on-device neural path via `NextWordSuggestionsPipeline`. The missing piece for “SwiftKey feel” is **merge + scoring** between typed-word completions and context-driven next-word candidates: today they’re mostly separate, and the next-word candidate pool is injected as an overlay inside `SuggestImpl.getSuggestions(...)`. If we want context to reliably win _when it should_ (without 1-letter-prefix chaos), weighting must happen in `SuggestImpl` (or below), not `SuggestionRefresher` (which only displays a list). First step: while composing, prefix-matching next-word candidates now _promote_ already-present typed suggestions into the gated injection slot (so context can re-rank completions for 2+ letter prefixes without destabilizing 1-letter prefixes). Second step: for 2+ letter prefixes, rerank prefix-matching typed suggestions by neural first-token log-prob (when scoring context is available) so context can reorder completions even when they weren’t in the top next-word list (`SuggestImpl.maybeRerankPrefixMatchingTypedSuggestionsByContext`). Third step: when neural scoring context is **not** available, rerank prefix-matching typed suggestions by the pipeline’s full next-word candidate pool order (so n-gram + legacy personalization/contacts still shape completions). A likely direction: unify candidates under one scorer (e.g., `score = unigram + context(previousWord→candidate)`), and gate how much context can dominate based on prefix length (so `t` stays stable, `th` can strongly prefer `the`). “Precompute next word while typing current word” is non-trivial; a closer SwiftKey analogue is using context to score _current_ candidates and/or showing next-word for the top completion.
