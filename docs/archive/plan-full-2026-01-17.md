# NewSoftKeyboard Plan (Architecture + Ownership + Refactor)

This file is the single source of truth for how the codebase is organized and how we keep refactors from turning into
unowned “helpers everywhere”.

## North Star

- Each module has a **singular purpose**.
- Each concept has an obvious **owner** (module + package + “host” class), so readers know “where to go” and refactors
  don’t create cyclical helper graphs.
- Compatibility with AnySoftKeyboard add-ons is preserved at the **external boundary** (intent actions/meta-data/XML),
  not by keeping internal class names forever.

## Quick Orientation (top owners)

If you’re unsure “where does this live?”, start here. The detailed rules and SoT map are below.

- **IME runtime / session state** (`:ime:app` → `wtf.uhoh.newsoftkeyboard.app.ime`)
  - Owns: editor session (`EditorInfo`/`InputConnection` routing), compose lifecycle, orchestrating feature controllers.
- **Keyboard selection + modes** (`:ime:app` → `wtf.uhoh.newsoftkeyboard.app.keyboards`)
  - Owns: current keyboard + mode resolution (`KeyboardSwitcher` is the only mode resolver).
- **View/touch/render** (`:ime:app` → `wtf.uhoh.newsoftkeyboard.app.keyboards.views`)
  - Owns: touch session state + rendering/layout math; talks upward via view-owned `Host` contracts only.
- **Next-word candidates (engine-agnostic pipeline)** (`:ime:nextword`)
  - Owns: candidate orchestration/normalize/merge/fallback; engines accessed via `:engine-core` only.
- **Add-on compatibility boundary** (`:api` + `:ime:addons`)
  - Owns: namespaces/actions/meta-data keys + add-on discovery/enabled sets; constants live only in `PluginActions`.

## Refactor Philosophy (architecture > packaging)

Architecture is boundaries and dependencies: who can call whom, what data crosses seams, and what invariants live
where. File size is packaging.

- We can have many small files with terrible architecture (tight coupling, circular deps, helpers everywhere). This is
  harder to fix because the “monolith” is now scattered.
- We can have larger files with decent architecture (clear layers, stable interfaces, owned state). These are much
  easier to split later.

We still shrink monoliths because large files tend to hide multiple concepts and implicit invariants. But we only
split when it creates a real seam with clear ownership and state.

## What We Are (and Are Not) Doing

- We are **not** “using upstream ASK” as a dependency. This repo is the source code for NewSoftKeyboard.
- We **do** keep runtime compatibility with installed ASK add-ons, so some legacy component names and action strings are
  intentionally retained (mostly in `askCompat` flavor and add-on discovery surfaces).

## Feature Plan: Context-aware Input Profiles (Per-app presets + secure API overrides)

Goal: let users create **presets** (text rules, dictionaries, layout/theme knobs) and bind them **per app**, while
optionally allowing _the focused app_ (or a paired automation controller) to request **session-only** changes via the
Programmable API (strict opt-in, allow-listed, rate limited, and audited).

### User stories (what “great” looks like)

- As a user: “Messages” uses shorthand rules (“how are you?” → “hru?”), while “Work email” keeps formal corrections.
- As a user: I can quickly see (and clear) any active preset override from the keyboard UI.
- As an app developer (opt-in): my app can request a session-only theme preset or layout, but only after the user
  explicitly grants that permission to my app.

### Research alignment / principles (security + UX)

- **Honor platform privacy signals**: treat `EditorInfo.IME_FLAG_NO_PERSONALIZED_LEARNING` as “incognito enforced” (already
  done by `ImeIncognito`) and ensure profiles/rules do not defeat that expectation.
- **Honor “no suggestions” fields**: `EditorInfo.TYPE_TEXT_FLAG_NO_SUGGESTIONS` should suppress suggestion-first UX and
  default-disable any “helpful” transforms unless the user explicitly opts in per preset/rule.
- **Respect secure input**: password fields must never run transformations, learning, or “smart” edits; this includes
  typed rules and voice post-processing.
- **Prefer user-visible outcomes**: if a rule is surprising, show it as a suggestion first; allow per-rule “auto-apply”.
- **Minimize data handling**: only inspect the minimum needed cursor context, never persist surrounding text, and never
  log it.

### Hard boundaries (security + privacy)

- Never expose typed text, composing text, clipboard contents, or target-app metadata via any API surface.
- Never allow silent persistent changes initiated by apps. App-driven changes are **session-only by default**.
- Never apply profiles in sensitive contexts:
  - password/secure fields (non-optional),
  - incognito mode (default: disabled),
  - `IME_FLAG_NO_PERSONALIZED_LEARNING` (default: disabled; treated as incognito).
- No new 3rd-party dependencies for this feature.

### Terminology

- **Input target app**: the app receiving text (`EditorInfo.packageName`).
- **Field selector**: a stable category derived from `EditorInfo.inputType`/variation and action (e.g., email/url/search/im/text).
- **Controller app**: the app calling the Programmable API (`caller_package`).
- **Preset**: reusable, user-defined configuration bundle.
- **Binding**: mapping from input target app + field selector → preset (v1 includes field selectors).
- **Session override**: temporary changes that automatically clear when the input target changes or the IME finishes.

### Threat model (what can go wrong)

- **Phishing / UI manipulation**: an app flips theme/layout to imitate another app or hide cues.
- **Denial-of-service**: override calls spam/flicker the UI or switch layouts repeatedly.
- **Over-broad automation**: a paired controller changes behavior while the user types in unrelated apps.
- **Sensitive text corruption**: rules rewrite OTPs/passwords/forms where correctness matters.
- **Rule complexity DoS**: expensive matching stalls the IME on commit (especially regex).
- **Data leakage via backups/logs**: user rules can embed personal info and should be protected from accidental export.

### Security configuration (defaults + guardrails)

We should implement explicit toggles with safe defaults:

- Global: `Context Profiles` **off by default**.
- Global: `Allow apps to control keyboard session via API` **off by default**.
- Global: `Disable profiles in incognito` **on by default**.
- Global: `Disable profiles when NO_PERSONALIZED_LEARNING` **on by default** (treated as incognito).
- Global: `Disable profiles in password fields` **always on** (non-optional).
- Global: `Disable auto-apply transforms when NO_SUGGESTIONS` **on by default** (allow explicit per-preset/per-rule opt-in).
  - Done (2026-01-14): per-preset opt-in (`allowAutoApplyInNoSuggestionsFields`, Settings → Context profiles → Preset → Security options).
- Per controller app (paired): allow-list which categories it can request (theme preset, keyboard id, preset id) and
  allow-list specific values (only the ids the user granted).
- Per controller app (paired): rate limit + UI cooldown + audit log entries (no payload text).
- Hard caps: limit presets/rules/bindings per device to prevent resource exhaustion (and keep all limits documented in UI).
  - Done (2026-01-13): enforced in `ContextProfilesStore` (`MAX_PRESETS=50`, `MAX_VOICE_RULES_PER_PRESET=50`,
    `MAX_TYPED_RULES_PER_PRESET=100`, `MAX_APP_BINDINGS=100`) and surfaced in Settings help/toasts.

### Design overview (context engine)

We build a small “context engine” inside the IME:

1. **Snapshot** current context: `packageName`, `inputType` class/variation, `imeOptions`, and local IME states
   (incognito, voice, etc.).
2. **Resolve** active preset with clear precedence:
   - session override (user UI / allowed API) →
   - per-app + field binding →
   - per-app “all fields” binding →
   - default preset.
3. **Apply** the resolved configuration to:
   - (A) text transformations (typed + voice),
   - (B) suggestion/dictionary sources,
   - (C) keyboard layout/mode,
   - (D) theme preset selection (note: per-app theme preset binding already exists; reuse that model).

### Preset contents (v1: explicit + allow-listable)

- **Text rules** (typed + voice)
  - Rule types (v1): exact phrase, word-boundary phrase, and “normalize punctuation/case” knobs.
  - Avoid user-defined regex in v1 (risk: IME stalls). If we later add “advanced patterns”, design a safe subset.
  - Triggers: “on commit boundary” (space/punctuation/enter/send) and “voice commit”.
  - Options: case handling, enable/disable per rule, and per-rule “auto-apply vs suggest”.
- **Dictionary/suggestions knobs**
  - Toggle existing sources per preset (e.g., user dictionary, contacts dictionary, quick-fixes/autotext).
  - Optional: per-preset word list (“profile user dictionary”) to bias suggestions in specific apps.
- **Layout / mode**
  - Optional keyboard id or mode (alphabet/symbols) to prefer when bound app is active.
- **Theme**
  - Prefer binding to existing theme preset ids; do not let apps request arbitrary colors.

### Field selectors (v1)

Bindings are per app _and_ per “field selector”, derived from `EditorInfo` (aligned with how `InputFieldConfigurator`
already classifies fields for keyboard modes):

- `all_fields` (fallback for the app; can be overridden by more specific selectors)
- `text` (default `TYPE_CLASS_TEXT`)
- `email` (`TYPE_TEXT_VARIATION_EMAIL_ADDRESS`/`TYPE_TEXT_VARIATION_EMAIL_SUBJECT`)
- `url` (`TYPE_TEXT_VARIATION_URI`)
- `im` (`TYPE_TEXT_VARIATION_SHORT_MESSAGE`/`TYPE_TEXT_VARIATION_LONG_MESSAGE`)
- `search` (`IME_ACTION_SEARCH` and/or `TYPE_TEXT_VARIATION_FILTER`)

Rule application still respects the global disallowed-context guards (password/incognito/NO_PERSONALIZED_LEARNING), and
`TYPE_TEXT_FLAG_NO_SUGGESTIONS` affects whether suggestion-first/auto-apply is permitted.

### Storage (no new 3rd-party deps)

- **Bindings + preset metadata**: direct-boot-aware `SharedPreferences` with JSON blobs (implemented in
  `ContextProfilesStore`, patterned after `KeyboardThemePresetAppBindingStore`).
- **Per-preset word lists** (if implemented): a dedicated SQLite file per preset id (keeps load cost bounded to active
  preset and avoids schema migrations of existing dictionaries).
- **Sensitive presets**: support marking a preset/rule set as “contains personal content” → exclude from backups/export
  by default (and never include in programmable API payloads).
  - Done (2026-01-14): per-preset `contains_personal_content` flag (default on); preferences backup skips sensitive preset JSON.

### Rule engine (safety + correctness)

- Apply rules only at commit boundaries (typed) or at voice commit time; never while composing candidates.
- Do not do disk I/O in the key path: compile rules into an in-memory matcher when the preset becomes active.
- Enforce guardrails:
  - max input length processed (e.g., last N characters/words),
  - max replacements per commit event (prevents loops),
  - max output length (prevents runaway expansions),
  - deterministic precedence order (stable results).
- Prefer suggestion-first for multi-word rewrites; default “auto-apply” only for rules the user explicitly marks as safe.

### IME integration points (where to hook)

- **Context changes**: `onStartInputView(EditorInfo)` is the primary seam (already used for per-app theme overlay).
- **Voice transcription**: apply “voice rules” immediately before `commitText` in voice triggers
  (`IntentApiTrigger` + `ThirdPartySpeechTrigger`) via `VoiceImeTextPrecommitProcessor` (after
  formatting/capitalization decisions are made).
- **Typed transformations**: apply “typed rules” only on commit boundaries (space/punctuation/enter) and editor actions
  (send/done/go/search), and ensure password/incognito/NO_PERSONALIZED_LEARNING guards are checked on every application.
- **Dictionaries**: extend dictionary setup to add/remove the active preset’s optional dictionary sources and invalidate
  caches on preset change (avoid per-keystroke churn; only on context transitions).

### Settings UX (user-owned + trustworthy)

New settings area: **Context Profiles** (name TBD), with:

- Preset list: create/rename/duplicate/delete presets; show last-used info and a “reset to safe defaults” action.
- Rule editor: add/edit rules with a preview playground (“input → output”), plus a per-rule “suggest/auto-apply” toggle.
- App bindings: searchable installed-app picker; bind app + field selector → preset (all fields/email/url/search/im/text);
  bulk manage bindings; add a “disable for this app” quick action surfaced from the keyboard UI.
  - UX note: allow an “All fields in this app” binding and then override specific field types as needed.
- Safety valve: provide a keyboard-accessible “temporarily disable context profiles” action in case a rule makes typing
  difficult.
- Safety UX:
  - show a persistent “Session override active” indicator on the keyboard when an app/controller changed theme/layout,
    with one-tap clear,
  - show warnings/confirmations for high-risk capabilities (layout/theme switching), and keep them off by default.

### Programmable API extension (optional, security-first)

We already have a paired, scoped Programmable API; extend it with **session-only** overrides that are narrow,
allow-listed, rate limited, and audited:

- New methods (examples): `setSessionPreset`, `setSessionThemePreset`, `setSessionKeyboardId`, `clearSessionOverrides`.
- New scopes: `context.session.preset`, `context.session.theme`, `context.session.layout` (split scopes is safer than one
  broad “write”).
- Mandatory guardrails:
  - **No bypass of pairing**: require the existing pairing + signature pin (and token if configured).
  - **Focused-app default**: require `caller_package == EditorInfo.packageName` unless a separate high-risk “automation
    controllers” toggle is enabled.
  - **IME must be active**: only apply session overrides when the IME is currently active for the target app (prevents
    background/async toggling while the user is not interacting).
  - **Session-only** by default; no persistent preference writes through these methods.
  - **No read-back**: do not add API methods to query the current preset, focused app, or resolved rules (prevents
    metadata leaks).
  - **Allow-list values** per controller: controller may only request ids explicitly granted by the user.
  - **Rate limit + UI cooldown** (per controller) and **audit log** every request and applied change (no text payload).
  - **Disallowed contexts**: password fields, incognito/NO_PERSONALIZED_LEARNING, and any other secure contexts we already
    block for injection actions.

### Rollout plan (reduce risk)

1. **Phase 1 (lowest risk):** per-app bindings for “safe toggles” + voice transcription rules (suggest-first).
2. **Phase 2:** typed commit-boundary rules with strict guards and conservative defaults.
3. **Phase 3:** per-preset dictionaries / word lists (load only when preset active).
4. **Phase 4:** API-driven session overrides for the focused app (scoped + allow-listed + audited).
5. **Phase 5 (optional):** paired automation controllers allowed to override in non-focused apps (high-risk toggle + per
   target-app allow-list).

## Taxonomy (where things live)

### Module Ownership (single purpose)

- `:ime:app` — the packaged Android app (manifests/resources/entrypoints), wiring, and thin orchestrators.
- `:ime:base`, `:ime:base-rx`, `:ime:prefs` — core shared IME infrastructure (preferences, reactive wiring, common utils).
- `:ime:dictionaries` (+ `:ime:dictionaries:jnidictionaryv1/v2`) — dictionary engines, persistence, JNI dictionaries.
- `:ime:nextword` — engine-agnostic next-word suggestions (legacy next-word dictionary + “candidate pipeline” utilities).
- `:engine-core` — prediction interfaces + data types (engine seam).
- `:engine-models` — shared model store/selection/download/verify; consumed by both `:engine-presage` and `:engine-neural`.
- `:engine-presage` — Presage/KenLM engine implementation (uses `:engine-models`).
- `:engine-neural` — ONNX-based engine implementation and tokenizer (uses `:engine-models`).
- `:ime:suggestions:presage` — Presage native binding boundary (JNI/CMake + vendored sources); no Java policy.
- `:ime:addons` + `:api` — add-on discovery and the compatibility facade (`PluginActions`) that defines legacy + NSK
  namespaces.
- `:addons:*` — in-tree add-on packs (languages/themes/quicktexts) that ship as separate APKs.

Rule of thumb: `:ime:app` should not “own” algorithmic logic; it should delegate to module owners above.

## Architecture Layers (dependency direction)

These layers are the mental model we use when carving monoliths. A “helper” is only good if it makes ownership more
obvious _within a single layer_, not if it becomes a cross-layer dumping ground.

**High-level direction:** UI → IME runtime → (views + switching) → (engines + dictionaries) → base/prefs.  
**Compatibility boundary:** add-on intents/meta-data live in `:api` and are consumed by discovery code.

- **UI layer** (`wtf.uhoh.newsoftkeyboard.app.ui.*`)
  - Owns: screens, settings UX, summaries, wiring to orchestrators.
  - Must not: implement engine/dictionary logic; keep work in owners below.
- **IME runtime layer** (`wtf.uhoh.newsoftkeyboard.app.ime.*`, `wtf.uhoh.newsoftkeyboard.app.ime.ImeServiceBase`)
  - Owns: lifecycle, editor state, input routing, high-level orchestration.
  - Must not: contain touch math/render code, or engine internals.
- **Keyboard switching/model layer** (`wtf.uhoh.newsoftkeyboard.app.keyboards.*`)
  - Owns: keyboard selection, modes, model data (not rendering).
  - Must not: depend on Android view classes.
- **View/touch/render layer** (`wtf.uhoh.newsoftkeyboard.app.keyboards.views.*`)
  - Owns: dispatch, gesture timing, drawing/layout math.
  - Must not: depend on IME service types; communicate via narrow `Host` callbacks/data.
- **Engines/dictionaries layer** (`:engine-*`, `:ime:dictionaries*`)
  - Owns: prediction/dictionary implementations and persistence.
  - Must not: depend on `:ime:app` UI/service classes.
- **Base/prefs infrastructure** (`:ime:base*`, `:ime:prefs`)
  - Owns: cross-cutting primitives (prefs, threading, small generic infra).
  - Must not: grow into feature logic.

### Package Ownership (within `:ime:app`)

- `wtf.uhoh.newsoftkeyboard.*` — NewSoftKeyboard branded entrypoints only (service/application/activity overlays) and thin
  delegates/wiring.
- `wtf.uhoh.newsoftkeyboard.app.*` — NewSoftKeyboard-owned internal subsystems that we intentionally keep out of the legacy
  `com.anysoftkeyboard.*` namespace (e.g., crash/notices/theme/keyboardextensions/quicktext/dictionaries/prefs backup/settings UI).
- `com.menny.android.anysoftkeyboard.*` — legacy entrypoints only (kept for upgrade stability and `askCompat`).
- `wtf.uhoh.newsoftkeyboard.app.ime.*` — IME runtime behavior (lifecycle, input routing, suggestions orchestration).
- `wtf.uhoh.newsoftkeyboard.app.keyboards.*` — keyboard model + switching; avoid UI here.
- `wtf.uhoh.newsoftkeyboard.app.keyboards.views.*` — view rendering + touch dispatch; keep “what to render” separate from “how to
  dispatch touch”.
- `wtf.uhoh.newsoftkeyboard.app.ui.*` — activities/fragments/settings; keep business logic out (push into module owners).

## Concept Ownership Map (make “who owns what” obvious)

This is the practical map used during refactors and extractions. If a new class doesn’t clearly fit one of these
concepts, we should stop and decide ownership before writing code.

- **IME lifecycle + editor state**
  - Owner: `:ime:app` / `wtf.uhoh.newsoftkeyboard.app.ime`
  - Hosts: `wtf.uhoh.newsoftkeyboard.app.ime.ImeServiceBase` (service), `EditorStateTracker` (state), `InputConnectionRouter` (routing)
  - Must not: reach into view rendering or engine implementations directly
- **IME preferences (reactive primitives + feature binding)**
  - Owner: `:ime:prefs` (storage + reactive primitives), `:ime:app` (feature-specific binding)
  - Hosts: `RxSharedPrefs` (primitive), binders like `ImePrefsBinder` / `SuggestionSettingsController`
  - Must not: hide “real state” in scattered helpers that each interpret prefs differently
- **Context profiles (per-app presets + session overrides)**
  - Owner: `:ime:app` / `wtf.uhoh.newsoftkeyboard.app.ime` (context snapshot + resolver + apply), `:ime:prefs` (storage),
    `:ime:dictionaries` (rule/dictionary primitives)
  - Hosts (planned): `ContextProfilesResolver`, `ContextProfilesStore`, `SessionOverridesStore`
  - Must not: do disk I/O on keystrokes, log user text, or expose focused-app metadata via API
- **Keyboard switching + mode resolution**
  - Owner: `:ime:app` / `wtf.uhoh.newsoftkeyboard.app.keyboards`
  - Hosts: `KeyboardSwitcher` (+ provider classes under `wtf.uhoh.newsoftkeyboard.app.keyboards.*`)
  - Must not: depend on Android view classes; expose narrow info needed by views
- **Touch dispatch + gesture/timing**
  - Owner: `:ime:app` / `wtf.uhoh.newsoftkeyboard.app.keyboards.views`
  - Hosts: `KeyboardViewBase`, `TouchDispatcher`, `PointerTracker` (low-level touch tracking)
  - Done (2025-12-21): extracted gesture-typing path state out of `PointerTracker` into
    `GestureTypingPathTracker`, making the touch pipeline’s “gesture typing vs. tap” seam explicit.
  - Done (2025-12-21): extracted the extension-keyboard popup touch state machine out of `KeyboardView` into
    `ExtensionKeyboardController` (thresholds, prefs wiring, popup-key setup) so the view stays a thin event host.
  - Must not: depend on IME service types; talk via a small `Host`/callback interface
- **Rendering + layout math**
  - Owner: `:ime:app` / `wtf.uhoh.newsoftkeyboard.app.keyboards.views`
  - Hosts: `KeyboardViewBase` and focused render components (e.g., dirty-region decisions, icon resolution, hint/name text)
  - Done (2025-12-21): extracted watermark state + drawing out of `KeyboardView` into `KeyboardWatermarks` so the view focuses on
    event wiring and delegates rendering details to a single owned component.
  - Done (2025-12-21): extracted gesture-trail state + drawing out of `KeyboardView` into `GestureTrailRenderer` so gesture typing
    visualization and the gesture-detector disablement rule live in one owner.
  - Must not: access preferences directly; consume a precomputed “render config”
- **Suggestions orchestration (IME-side)**
  - Owner: `:ime:app` / `wtf.uhoh.newsoftkeyboard.app.ime`
  - Hosts: `ImeSuggestionsController`, `SuggestionsProvider`
  - State SoT: `SuggestionsSessionState` (prediction/correction/selection expectations + dictionary-load state)
  - Must not: embed engine-specific logic or pipeline algorithms (normalization/merging/fallback belong below)
- **Word composing state**
  - Owner: `:ime:dictionaries` / `wtf.uhoh.newsoftkeyboard.dictionaries`
  - Host: `WordComposer`
  - Must not: be duplicated inside IME runtime state
- **Legacy next-word dictionaries (user/contacts)**
  - Owner: `:ime:nextword` / `wtf.uhoh.newsoftkeyboard.nextword`
  - Hosts: `NextWordDictionary`, `NextWordsStorage`, `NextWordSuggestions`, parsers/stats

## Dependency Rules (to prevent cyclical ownership)

- UI (`wtf.uhoh.newsoftkeyboard.app.ui.*`) may depend on orchestrators/services, but not on implementation details inside engines.
- Engines (`engine-*`) must not depend on `:ime:app` classes.
- “View” code must not pull in IME service types directly; it talks to narrow `Host` interfaces.
- Add-on compatibility is centralized in `:api` (`PluginActions`). No scattered action/meta-data strings.

## Monolith Carving Playbook (how we make splits safe)

The goal is not “many small files”. The goal is clear seams with owned state. We shrink files by _creating seams_,
not by scattering logic.

0. **Name the concept + owner** (module + package + host). If we can’t name it, stop.
1. **Identify the state/invariants** of the slice and make it explicit.
   - Prefer a single `*State`/`*Session` object for mutable state.
2. **Shrink in place first**:
   - Prefer a `private static` nested class, or a package-private top-level class in the same package as the host.
   - This reduces size without widening dependencies/visibility.
3. **Define the boundary**:
   - Introduce a narrow `Host` interface/callback surface to prevent back-references across layers.
4. **Promote to a standalone file/module only when earned**:
   - When it becomes reusable or independently testable, and still has one owner.
5. **Keep it shippable**:
   - Build/tests after each slice; avoid “big bang” rearrangements that leave broken intermediate states.

## Helper Policy (to stop “helpers everywhere”)

- Default posture: **don’t extract** — keep code as a private method inside the owning host until there is a concrete
  reason to create a new class.
- No new generic `*Utils`/`*Helper` without a clear owning concept and a clear home.
- Every extracted class must answer:
  1. **Who owns it?** (file/package/module)
  2. **Who calls it?** (host)
  3. **What does it own?** (state vs stateless)
  4. **What does it NOT know?** (forbidden dependencies)
- Prefer **components** with a small constructor and a `Host` interface over static helpers.
- Prefer **package-private** classes in the same package as the host over widely visible “shared helper” packages.
- Prefer a **private static nested class** when something is strongly coupled to one host and not reused yet; promote it
  to a top-level class only when it becomes independently reusable/testable.
- If a helper starts being used by multiple concepts, it probably belongs in a module owner (`:ime:base`, `:ime:prefs`,
  `:engine-core`, etc.) or needs to be split.
- Avoid “helpers calling helpers”. One level of delegation is enough; if a refactor creates a chain of indirections,
  stop and re-assign ownership so the host talks to a single owned component.

## Existing Helper Sprawl Remediation (backlog)

We already have some “helper sprawl” (generic `utils`/`helpers` packages and helper chains). The fix is not “move
everything into more helpers”; it’s to collapse ownership back into a few SoT owners and make boundaries explicit.

### How we do it (repeatable loop)

1. **Inventory**
   - List candidate sprawl files: names containing `Utils/Util/Helper` and packages named `utils`/`helpers`.
   - Identify the _highest fan-in_ ones (imported from many unrelated places) and the ones that cross layers.
2. **Assign an owner**
   - For each candidate, pick the owning concept/module from the Concept Ownership Map.
   - If it has multiple unrelated callers, split it by concept; do not leave it as a “shared helper”.
3. **Localize + narrow**
   - If it’s only used by one host: make it package-private or a `private static` nested class in the host.
   - If it’s genuinely foundational: keep it, but move it to the correct “base” owner and keep it dependency-clean.
4. **Remove helper chains**
   - Collapse “helper calling helper” stacks into a single owned component per concept.
5. **Build/tests after each slice**

### End state (definition of done)

- `:ime:app` has no generic `wtf.uhoh.newsoftkeyboard.utils` dumping ground; app owns wiring/UI/runtime only.
- Any remaining `utils` in base are small, dependency-clean primitives (no feature logic).
- There is no `helpers` package whose contents belong to different concepts.
- A reader can find any non-trivial logic by going to the concept owner (not by grepping for helper names).

## Ownership Checklist (PR/review gate)

Every refactor slice should satisfy this checklist before it is considered “done”:

1. A file/class moved out of a monolith has a **named concept** from the Concept Ownership Map.
2. The extracted code has **one obvious host** (not multiple unrelated callers).
3. Imports do not cross forbidden boundaries (e.g., view code does not import IME service types).
4. The original monolith no longer contains the same logic (no “two copies”).
5. The extraction did **not** introduce a new cross-cutting `*Utils`/`*Helper` to make compilation easy.
6. If the class is shared, it lives in the appropriate owning module/package (not in `:ime:app` “because it was easy”).

## Naming & Compatibility Policy (why ASK names still exist)

- We keep legacy class/component names **only** when they are externally visible or upgrade-critical:
  - manifest component entrypoints, intent actions/meta-data, preferences keys, and add-on contracts.
- Internal architecture should converge on NSK naming _by concept ownership_, not by mass renames:
  - rename when the owner is clear and we can provide a stable alias/migration.
- A file/class still named `AnySoftKeyboard*` (mostly test runners and legacy entrypoints) is not “upstream ASK usage”; it is
  technical debt retained for upgrade stability while we carve the monoliths into owned components.
