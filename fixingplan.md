# Fixing Plan — Text Suggestions (Typed + Next-Word) and Language-Pack Dictionaries

This plan replaces any prior `fixing_plan.md` content.

## Status (as of 2026-02-27)

- P0 (runtime filtering/ranking): done
- P1 (dictionary de-noising at generation time): done (abbreviation flags)
- P3 (validation via report harnesses): done (typed + next-word suites)
- P2 (update underlying wordlists): optional / pending (only if dictionary quality is still not good enough after P0/P1)

## Problem statement

Our “text suggestions” are the combination of:

- **Typed/current-word suggestions** (completions/corrections while composing).
- **Next-word suggestions** (predictions after a word is committed).

Even if next-word prediction is good, typed suggestions can still feel broken if:

- the underlying language-pack dictionary contains noisy tokens (acronyms, domains, odd proper nouns), and/or
- our typed-suggestion ranking/filters let those tokens surface in normal text fields.

## Where the “installed language pack dictionaries” come from (English example)

English is bundled into the app (`ime/app/build.gradle` depends on `:addons:languages:english:pack`), and its shipped
typed-suggestion dictionary is a **static frequency lexicon** (not an LLM):

- Runtime binary dictionary resources:
  - `addons/languages/english/pack/src/main/res/raw/english_words_1.dict`
  - `addons/languages/english/pack/src/main/res/raw/english_words_2.dict`
- Dictionary manifest:
  - `addons/languages/english/pack/src/main/res/xml/english_dictionaries.xml`

Those `.dict` binaries are generated by the Gradle `make-dictionary` plugin from:

- AOSP/LatinIME-format unigram list:
  - `addons/languages/english/pack/dictionary/en_wordlist.combined.gz`
- Prebuilt additions (merged into the dictionary today):
  - `addons/languages/english/pack/dictionary/prebuilt/additionals.xml`
  - `addons/languages/english/pack/dictionary/prebuilt/websites.xml`
- Text corpora used to count/merge additional tokens:
  - `addons/languages/english/pack/dictionary/inputs/*`

Important pipeline detail:

- `buildSrc/src/main/java/GenerateWordsListFromAOSPTask.java` is the parser that converts AOSP `*.combined.gz` unigram lists
  into XML wordlists before they get merged into the final `.dict` binaries.
- AOSP `flags=...` matter: treating `flags=abbreviation` (etc.) like normal words can cause noisy ALL‑CAPS acronyms to
  dominate typed-suggestion candidate pools. We now parse `flags=...` and downweight ALL‑CAPS abbreviations.

## What we can do to improve it (prioritized)

### P0 — Runtime ranking + filtering (best ROI; works even if dictionaries are mediocre)

Goal: keep typed suggestions “normal” in normal text fields:

- Suppress unrelated **ALL‑CAPS acronyms** unless the user is actively typing in ALL‑CAPS.
- Suppress **domain/web fragments** (`.com`, `http`, `www`, full domains from `websites.xml`) in normal text fields;
  allow them only in URL/email fields (or once the user types `.`).
- Suppress **punctuation-only** candidates unless the user is typing punctuation.
- Fix ranking pathologies where common completions are demoted for non-user-visible reasons (e.g. length thresholds).

Status (already implemented):

- Prefix-completion scoring no longer creates “tier split” ordering where `tha` ranks `thaw` above `that's` simply
  because `that's` is longer. Prefix completions now treat “distance” as “extra characters” for boosting.
- ALL‑CAPS acronym suppression now triggers whenever the user is not typing ALL‑CAPS (so sentence-start “Tha” won’t
  surface “TNA”).
- Punctuation-only candidates (e.g., `|`) are filtered out while composing normal words.
- Domain-like tokens (e.g., `com/http/www` and full domains like `google.com`) are filtered out in normal text fields,
  but still allowed in URL/email fields (and when the user is already typing URL-like text).

### P1 — Dictionary generation de-noising (fix the source, not just the UI)

Goal: prevent the worst tokens from ever entering the main typed-suggestion dictionary.

1. Teach the AOSP wordlist parser to respect flags:
   - Update `buildSrc/src/main/java/GenerateWordsListFromAOSPTask.java` to parse `flags=...`.
2. Apply conservative policies when generating the main dictionary:
   - Skip or heavily downweight `flags=abbreviation` tokens that are **ALL‑CAPS** and length ≥ 3.
   - Consider skipping `flags=nonword` and `flags=offensive` for the default dictionary output.
3. Treat `prebuilt/websites.xml` as field-specific data:
   - Option A (cleanest): keep domains out of the main dictionary and surface them only in URL/email modes.
   - Option B: keep them merged but tag/identify them and filter at runtime by input field type.

Status (already implemented):

- `GenerateWordsListFromAOSPTask` now parses `flags=...` and heavily downweights ALL‑CAPS `flags=abbreviation` tokens
  (e.g., `TNA`, `TNA's`) so they stop dominating correction candidate pools.

### P2 — Update the underlying wordlists (modernize lexicon + frequencies)

Goal: get newer, higher-quality frequency data so the baseline suggestions are better.

We already have a repo tool + CI workflow for this:

- CI workflow: `.github/workflows/update_aosp_dictionaries.yml`
- Updater tool: `js/update_aosp_dictionaries/`

Manual update commands (same sources CI uses):

```bash
# AOSP LatinIME dictionaries
bazel run //js/update_aosp_dictionaries -- update \
  --dictionaries_archive https://android.googlesource.com/platform/packages/inputmethods/LatinIME/+archive/refs/heads/main/dictionaries.tar.gz \
  --dictionaries_mapping "${PWD}/js/update_aosp_dictionaries/aosp_mapping.yml"

# LineageOS LatinIME dictionaries (extra languages)
bazel run //js/update_aosp_dictionaries -- update \
  --dictionaries_archive https://github.com/LineageOS/android_packages_inputmethods_LatinIME/archive/refs/heads/lineage-22.2.tar.gz \
  --dictionaries_mapping "${PWD}/js/update_aosp_dictionaries/lineage_mapping.yml"
```

Then regenerate the English pack dictionary:

```bash
./gradlew :addons:languages:english:pack:makeDictionary
```

Notes:

- The updater expects an **absolute** mapping path (see the CI workflow for the working invocation).
- English-only mapping (useful to keep diffs small when you only care about English):
  - `js/update_aosp_dictionaries/aosp_mapping_english_only.yml`
- Local check (2026-02-27): AOSP `en_wordlist.combined.gz` was already identical to our repo copy, so this step made no changes.

### P3 — Validation and acceptance criteria (make improvements measurable)

We should not “feel” our way through suggestion changes. Use the existing typed-suggestions report harness:

- Genymotion runner (renders + uploads HTML):
  - `scripts/genymotion_typed_suggestions_report.sh`
  - Example: `ONLY_CASE_ID=plain-tha scripts/genymotion_typed_suggestions_report.sh`

Acceptance checks:

- `tha` should show `that/that's/than/thanks/thank/...` (no symbol noise, no unrelated ALL‑CAPS acronyms).
- Titlecase `Tha` should still **not** show `TNA` (unless the user is typing ALL‑CAPS).
- Domains should not appear in normal text fields; they should appear in URL/email fields (or after typing `.`).

Key finding (answers “does the engine see previous words in the editor?”):

- In normal text fields, we can best-effort **read existing editor text** (`getTextBeforeCursor`, with a fallback to
  `getExtractedText`) and **seed the next-word engine** with the last N tokens.
- Seeding is correctly **blocked** for privacy-restricted cases (password fields, incognito, `IME_FLAG_NO_PERSONALIZED_LEARNING`,
  and `TYPE_TEXT_FLAG_NO_SUGGESTIONS`).
